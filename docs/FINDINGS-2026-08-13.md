## VRF READS COMPILED RESOURCES, and the payload is a normal KVObject — `[V-CI]` probe-compiled 2026-08-13

The API, now READ rather than guessed:

```
ValveResourceFormat.Resource           12.0.0.0
  Read(string) / Read(Stream, bool)
  Blocks : List<Block>                 GetBlockByType(BlockType)
  DataBlock : ResourceData             ResourceType, Version, EditInfo
  ExternalReferences : ResourceExtRefList
```

For a `.vdata_c`, `DataBlock` is a `ValveResourceFormat.ResourceTypes.BinaryKV3`,
and **`BinaryKV3.Data` is a `KVObject`** — the same type `Kv3Document` already
walks for source vdata.

**Consequence: map reading reuses the vdata layer.** `Flatten`, `Resolve` and
`TryRead` work unchanged once a document is loaded, so no second reader is
needed and `Kv3Document` can remain the only file touching VRF.

Blocks in a compiled vdata: `RED2` (edit info), `DATA` (the payload), `FLCI`.

**Pointing the SOURCE parser at a compiled file throws
`ArgumentOutOfRangeException` (`Parameter 'index'`)** — an unhelpful exception
with no format-specific meaning. `Kv3Document.Load` already wraps it, but its
message ("compiled .vdata_c is not supported") is now misleading: compiled is
readable, just not implemented in the shipping tool.

### Not yet decided, deliberately

A compiled-load path in `Kv3Document` would be **read-only by construction** —
writing compiled resources is where VRF is weak and the project's answer has
always been to route through `resourcecompiler` instead. The design was
grilled and settled in principle:

- a distinct type that structurally cannot be written, sharing traversal
- detect compiled by **sniffing the header**, not by the `_c` extension
  (extension is a hint for the error message only)
- `set` and `batch` refuse it; `diff` and a future `map info` accept it

**Not built.** There is no consumer today: GameTracking ships source vdata, so
the pipeline already has the better input. Build it when map reading needs it.

## Source-vs-compiled diff — PROBED, INCONCLUSIVE

The idea: `dl diff --old x.vdata --new x.vdata_c` reporting zero differences
would be a strong, falsifiable claim that **compilation preserves values**.
That is a real gap — `loop` proves patched and pristine compiled output DIFFER,
never that they differ CORRECTLY.

The probe reported 0 differences. **Do not treat that as evidence.** It ran
against `game_asset_tags.vdata`, which flattens to **one path**
(`generic_data_type`) — the file's own type declaration, the one key certain to
survive. It confirms the flatten works on both sides and nothing more.

`diff-smoke` guards against exactly this with `assert old_paths > 100`; the
probe should have carried the same floor and did not.

**To settle it:** re-run against `heroes.vdata` (12,090 float candidates) or at
least `nav_hulls.vdata` (12). Both compile; `loop` already compiles both.
Worth doing only if the cross-boundary diff is actually wanted.

## CI harness — path translation on windows-latest

**Do NOT pass Unix absolute paths between Git bash and Windows Python.** Git
bash resolves `/tmp` through its MSYS mount table; Windows Python reads
`/tmp/x` as `C:\tmp\x`. A redirect writes somewhere the interpreter cannot see:

```
FileNotFoundError: [Errno 2] No such file or directory: '/tmp/p1.json'
```

Relative paths are unambiguous to both. Cost one run, 2026-08-13.

## Stage compiled artifacts IMMEDIATELY after compiling

`loop` compiles a patched file, then compiles the pristine original to prove
the outputs differ — which **overwrites the compiler's output directory**. Any
staging that happens after that point picks up the pristine artifact.

Stage into the curated pack tree in the same step as the compile, before
anything else can touch `DEFAULT_WRITE_PATH`. This is the same lesson as
"pack from a curated tree", one stage further along.

## First measurements — 2026-08-13

Three numbers now recorded on every relevant run. Baselines:

| measurement | first reading | note |
|---|---|---|
| peak working set, batch | **63 MB for 2 files** | one of them `heroes.vdata`. Mostly .NET runtime baseline; marginal cost per hero-sized document is well under 30 MB, so the 32-file cap (Q13) is **conservative, not optimistic** |
| time to first assertion, `loop` | **32 seconds** | was several minutes: the CSDK download used to precede any validation. This is the number that costs a round trip |
| job duration | recorded by GitHub | CSDK now cached on `actions/cache`, key `csdk-12-v1`. Bump the key if the tree is ever wrong |

**"Optimised" was a decorative goal.** Nothing had ever been measured, and the
only performance-relevant finding on record — `PackageEntry.CRC32` licensing
index-only diffing — is unused, because `dl diff` fully parses both files
instead. That divergence was never noticed or written down.

The honest reframing: the binding constraints are **CI wall-clock, token cost,
and human round-trips**, not CPU. The goal is *cheap to iterate*, and the three
numbers above measure that. Parse throughput and VPK write speed are fast
enough that measuring them would create the illusion of optimisation work while
the real cost sits elsewhere.
