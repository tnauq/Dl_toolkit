## 1. An honest design review, and what it found

The three original goals were assessed against what exists. Recorded because
two of the answers changed how the project describes itself.

| goal | verdict |
|---|---|
| **Modular** | Modular by LAYER, not by TOOL. The layering is real and CI-enforced — Format owns ValvePak, `Kv3Document` is the only file touching VRF, and that held under pressure. But `dl-patch` had become a monolith with a misleading name, `Envelope.cs` a dumping ground, and four near-identical `Emit`/`Misuse`/`Fail` implementations existed |
| **Optimised** | **No, and unmeasured.** Nothing had ever been benchmarked. The one performance finding on record (`PackageEntry.CRC32` licensing index-only diffing) is unused — `diff` fully parses both files instead — and nobody had noticed the divergence |
| **Agent-friendly** | Strongest of the three. JSON envelope, distinct exit codes, `--dry-run`, deterministic ordering, `fix` on every error, and guards that let an agent detect its own staleness. **One self-inflicted wound:** error handling branched on message TEXT |

All four issues were fixed this session. See §2.

**"Optimised" is retired as a goal.** It was decorative. The binding constraints
are CI wall-clock, token cost and human round-trips; the replacement framing is
**cheap to iterate**, and it is now measured.

## 2. What was fixed

| | |
|---|---|
| **Text-matching removed** | `EditFailure` enum in `Edit.cs`; `EditResult` carries it. `Kv3Document` sets it at every failure site. Both front ends branch on the enum. **Rewording an error can no longer change an exit code** |
| **One emit path** | `CommandIo` owns envelope construction and the JSON/stderr branch. Commands pass `body` and `footer` callbacks — split that way to preserve the existing items-then-error-then-summary ordering. Exactly one `Json.ToStdout` in the codebase |
| **Renamed** | `AssemblyName` and `Tool.Name` are now `dl`. Project, namespace and directory stay `Deadlock.Patch` — those are baked into `patch-smoke`'s paths filter and every delivery path, and an assembly name differing from its project name is ordinary in .NET |
| **`patch-smoke` paths filter** | `src/Deadlock.Contracts/**` and `src/Deadlock.Format/**` added. A Contracts change could previously break v1 without triggering the test that catches it |
| **Three measurements** | peak memory in the batch envelope, time-to-first-assertion in `loop`, CSDK cached. `loop` reordered so cheap validation runs BEFORE the 261 MB download |

### On splitting vs renaming

Splitting `dl` into four binaries was considered and **rejected**: every new
assembly needs VRF and therefore net9, `Kv3Document` would have to move to a
shared layer (breaking the one-file-touches-VRF invariant), four binaries means
four copies of the CLI conventions, and CI setup cost is per-job. The monolith
is coherent — one binary, four modes, one document layer, one envelope. Only
the NAME was wrong.

## 3. `loop` now proves something worth proving

It previously ran on whichever tiny vdata the picker found first. It now runs a
**two-file atomic plan over `heroes.vdata` plus one other real file**, which
exercises cross-file atomicity and per-file reporting against real documents
for the first time — every prior multi-file assertion was synthetic.

Assertions added: the plan spans two distinct files; the hero target's path
starts with `hero_`; both edits carry non-null guards; batch reports
`files_total: 2` with every file written; both files compile; both differ from
their pristine compiles; the VPK holds exactly two `.vdata_c` entries, one of
them hero data, each matching its staged artifact **byte-for-byte**.

## 4. Maps track — opened

Settled by grilling, then partly answered by inspecting a real GameBanana map
mod locally (**never committed** — it is another modder's work).

| | |
|---|---|
| **Hammer is not on the critical path** | It cannot run on iOS and the track cannot wait. Phase 3 starts at the parametric `.vmap` emitter, with map READING first |
| **The emitter is mandatory, not optional** | A published map contains no recoverable source — the `.vmap_c` is a stub with an EMPTY `DATA` block. There is no route from someone else's map back to editable source |
| **Map compile is unprobed** | Whether `resourcecompiler` builds a `.vmap` headlessly is the probe that decides if the track is phone-drivable. `gameinfo.gi` declares `bakedlighting`, `nav` and `vis` builders by default |
| **First tool is `dl map info`** | Read before emitting. It also produces the bounding-box measurement FINDINGS lists as a known unknown |
| **"Structurally valid" for a map** | Target: compiles, passes spatial assertions, renders a plan-view PNG for review. First milestone: compiles |
| **First geometry target** | A sealed room with two spawns. If that will not load, nothing else matters |
| **Fixtures** | Derive facts, never commit someone else's map. Matches existing practice with GameTracking |

Full map anatomy in `docs/FINDINGS-maps-2026-08-13.md`. The headline: our
`dl pack` entry-path inference is **confirmed against a shipping addon**, and a
map ships as a **nested VPK** inside the addon.

## 7. Process

The four lessons held. Lesson 4 (**dump the real file before writing code that
depends on its shape**) was applied deliberately three times today — reading
`gameinfo.gi` to settle path resolution, dumping `Edit.cs` before touching
`EditResult`, and reflecting over VRF's surface in the probe before writing
against it. Each worked first time. Every failure this session was in
scaffolding written against an imagined shape, never in code written against a
read one.

**A fifth, from the probe:** *state the floor a measurement needs before
reading it.* The source-vs-compiled probe reported "0 differences — identical"
from a file with ONE path. `diff-smoke` guards this exact trap with
`assert old_paths > 100`; the probe was written without the same floor and
produced a confident, meaningless verdict.
