## Compiling — THE GAP IS CLOSED, `[V-CI]` probe-compiler 2026-08-12

FINDINGS previously recorded `resourcecompiler.exe` as running headless but
unable to build, with the missing `gameinfo.gi` called "the ONLY remaining gap".
That was three gaps in a trench coat. All are now closed and a real compile
succeeded:

```

OK: 1 compiled, 0 failed, 0 skipped
```

### 1. `-game` works, and names the directory HOLDING gameinfo.gi

`-game build/game/citadel` is correct. `-game build/game` fails instantly with
the original "Can't find gameinfo.gi" error. The file itself is fetched from
GameTracking-Deadlock (`game/citadel/gameinfo.gi`) rather than hand-written —
a synthesized approximation the compiler rejects is indistinguishable from the
compiler rejecting the flag.

### 2. `modtools.dll` is NOT in the Reduced CSDK — `[V-CI]`

The compiler died at `CAppSystemDict:Unable to load module modtools
(Dependency of application), error 126` (ERROR_MOD_NOT_FOUND).

- **Zero matches** for `*modtools*` across the CSDK's **128 real DLLs**.
- Retrying with both bin directories on `PATH`, and again with the compiler's
  directory as CWD, failed **identically** — which rules out DLL resolution as
  the cause. `LoadLibrary` searches the exe directory and `PATH`, NOT the
  `EXECUTABLE_PATH` entries the compiler prints; that theory was tested and is
  wrong here.
- The `bin_cs2` upload is complete and checksum-verified. Only `bin_cs2` was
  ever uploaded; modtools lives elsewhere in the CSDK tree.

**Resolution:** `modtools.dll` is now a **loose release asset on the `csdk-12`
tag**, copied beside the compiler by the fetch step. Its own static imports are
only `KERNEL32.dll` and `tier0.dll`, and tier0 is already in `bin_cs2/win64`,
so no further missing module is predictable from the binary. 1.2 MB, x64.

### 3. Path resolution — READ OFF gameinfo.gi, `[V-CI]`

`gameinfo.gi` comments that search paths are relative, and declares:

```
SearchPaths
{
    Game    citadel
    Game    core
}
```

Cross-referenced against the table the compiler prints, the rule is:

| | |
|---|---|
| `GAMEROOT` | the **current working directory** |
| `GAME` | `GAMEROOT\citadel` and `GAMEROOT\core` |
| `CONTENT` | `GAMEROOT\..\content\<game>` |

**Therefore the compiler must be RUN FROM the directory containing `citadel/`**
— i.e. `build/game`. Every earlier failure was working directory. Running from
the repo root put `CONTENT` outside the repo entirely, and

```
WARNING: Failed to split full path "...\probe.vdata" while initializing
FS: Tried to FileExists NULL filename!
```

is the compiler saying the input lies under no content mount. Run correctly it
reports the split it made:

```
ContentRoot = build/content/    ModName = citadel    RelativePath = scripts/...
```

`Game core` is a real second mount: `build/game/core/gameinfo.gi` must exist
too, and it is in the tracking repo.

## `KVValue` is a STRUCT — `[V-CI]` build 2026-08-12

`KVValue?` therefore means `Nullable<KVValue>`, not a nullable reference.
Writing `out KVValue?` and then reaching for `.Flag`/`.Type` produces seven
`CS1061`s plus a `CS0184` claiming an `is KVObject` test can never be true —
because `.Value` binds to `Nullable<T>.Value`. Declare it plain and initialise
with `default`.

The original code got this right by using `var`. It broke when the type was
written out by hand: `var` had been carrying information that was discarded.

`VpkWriter.CreateFromDirectory` packed a compiled `.vdata_c` and `--verify`

## Addon VPK entry paths — `[I]`, NOT confirmed against a running game

Entries are keyed **relative to the pack root**, forward-slashed —
`scripts/heroes.vdata_c`, not `citadel/scripts/...` and not absolute. This is
consistent with how `gameinfo.gi` mounts `citadel` as a search path, and with
where `resourcecompiler` writes (`DEFAULT_WRITE_PATH` = `game/citadel`). It is
**inferred**. `dl-patch pack --prefix` exists for when a real addon proves it
needs one.

## PACK FROM A CURATED TREE, never the compiler's output directory — `[V-CI]`

Two defects, both found by CI on the first green run of `loop`:

1. `--in build/game/citadel` packed **`gameinfo.gi`** into the addon. That is
   game configuration, not mod content, and must never ship inside an addon.
2. The packed resource was the **pristine** build, not the patched one — 1501
   bytes instead of 1524. The pristine recompile used for the differ assertion
   had overwritten the compiler's output before pack ran.

**The run was fully green while shipping the wrong file.** Every assertion held;
none asked which version landed. `loop` now stages a curated `packroot/` from
the patched artifact and asserts both the absence of `gameinfo.gi` and that the
packed entry length equals the patched artifact's.

Generalised: the compiler writes into the game tree, which is full of things
that are not yours. Stage what you mean to ship.

## CI harness facts — cost several red runs each

### `bash -e` is not cleared by `set -uo pipefail`

GitHub runs steps as `bash -e`. A bare `cmd` followed by `RC=$?` **kills the
step** the moment cmd exits nonzero, so `RC` is never read. Every negative
assertion in `batch-smoke` failed this way while the tool was behaving
correctly. Use:

```bash
RC=0
cmd || RC=$?
```

`cmd` on the left of `||` is `-e`-safe.

### Print output BEFORE asserting

A step that redirects to a file, asserts, and only then `cat`s will never show
the file when the assertion fails. `cat` first, assert second.

### The mobile Actions view renders neither step summaries nor dispatch inputs

`$GITHUB_STEP_SUMMARY` is invisible on a phone — use `upload-artifact`.
`workflow_dispatch` **inputs** are also not rendered, so a workflow requiring an
input cannot be run from mobile at all. Hardcode the parameter in `env:` and
edit the file instead.

### `python3` may not resolve in Git bash on windows-latest

Resolve it: `PY=$(command -v python3 || command -v python)`.

### `patch-smoke` has a `paths:` filter

It only fires on `src/Deadlock.Patch/**` and its own file. **It does not include
`src/Deadlock.Contracts/**`**, so a Contracts change can break v1 without
triggering the test that would catch it. Add that path.

It also hardcodes `hero_base.m_mapStartingStats.EMaxHealth` at `780.0` from a
2026-08-09 commit, which breaks whenever Valve moves the value.
`tools/pick_target.py` now exists to derive a target instead.
