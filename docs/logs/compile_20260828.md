# First real compile attempt — 2026-08-28

The log, trimmed. It never reached a map compile, but it got further than CI
ever has and it names its own blockers.

## The three lines that matter

    Unable to find fgd file citadel.fgd!
    Unable to find fgd file models_gamedata.fgd!   (x3)
    Failed loading resource "materials/error.vmat_c" (ERROR_FILEOPEN)

...followed by roughly 90 more `Failed loading resource` lines, every one a
core material or shader under `materials/dev`, `materials/tools`,
`textures/dev` or `soundevents`.

    Encountered accessviolation.
    Wrote minidump to .\resourcecompiler_2026_0828_151638_0_accessviolation.mdmp
    exit: 124

## What it means

**Step 3 of READ ME FIRST was not done.** The CSDK has no game content: no
`materials/error.vmat_c`, no `surfaceproperties.vsurf_c`, no soundevents
manifest. That is the `pak01_dir.vpk` export through Source 2 Viewer into
`Reduced_CSDK_12/game/citadel`, then re-extracting the CSDK's own
`game/citadel` over the top. Until that is done nothing will compile, and the
access violation is very likely a null resource handle rather than anything
to do with our map.

**The FGDs must live in the CSDK, not just in this repo.** `gameinfo.gi` line
194 declares `"fgd" "citadel.fgd"` relative to the GAME path, so the
compiler wants it at `Reduced_CSDK_12/game/citadel/citadel.fgd`. The copies
under `docs/reference/citadel/` are for `tools/fgd_check.py` and for reading;
they are not on any search path the compiler uses.

**`models_gamedata.fgd` is missing entirely** and is asked for three times.
It is not among the thirteen FGDs we hold. READ ME FIRST credits
"Additional files/Gamedata.FGD" to @DirtKiller23, so it ships with the CSDK
somewhere — worth finding, and worth adding to `docs/reference/citadel/`
once found.

**`exit: 124` is a timeout kill**, not a compiler exit code. Something hung
after the access violation. Whatever wrapper imposed that timeout should be
given a longer one on the next attempt, so the crash is seen rather than the
kill.

## The genuinely good news

    - citadel\maps\dust2.vmap
    Initialized Embree v4.04.00.

It found our map and loaded Embree, which is the raytracing library used for
lighting. So the invocation is right and the map was picked up. There is not
a single parse error, entity error or unknown-classname complaint anywhere in
the log.

**That absence is not evidence of a clean map.** With `citadel.fgd` unloaded,
the compiler had no entity table to validate against, so it could not have
complained about a classname or keyvalue even if one were wrong. Entity
validation on this run was effectively switched off — which is exactly the
gap `tools/fgd_check.py` exists to fill.
