Resume here for **entities, paths and the emitter**. The blockout, walkability,

## 1. What is settled

**dust2_full emits at scale.** 4,179 boxes, 75,236 elements, 49.5 MB of
keyvalues2_noids text, through `dmxconvert` to a 16.4 MB binary `vmap 40` and
back, census identical, every box verified within 0.1 u on origin, extents,
angles and material. The 3,201 rotated boxes survived, so pitched ramps are
not a special case. `emit-dust2.yml`.

**Paths work, and cost no GUID machinery.** A lane is a `CMapPath` whose
`children` are `CMapPathNode` elements; the route is the node order, not a
keyvalue. `MapEmitter` writes the nodes INLINE, so each is referenced once and
needs no id. `path-smoke.yml` is green: 3 paths, 10 nodes, zero element ids,
zero guid references, node order preserved through the round trip.

**CVisibilityMgr can stay empty.** In dl_example its `nodes` array is
exhaustive — 765 references, which is every root node plus all 349 path nodes,
minus the 2 `CMapGroup`. That looked like it might be required. It is not: a
string scan of every CSDK binary found `CVisibilityMgr` in exactly the same 16
binaries as the controls `CMapMesh` and `CMapEntity`, all of them tools
(hammer, resourcecompiler, dmxconvert, vrad3...), and found NONE of the
`CMap*` family in `engine2.dll` or `deadlock.exe`. The runtime does not know
these types. `symbol-scan.yml`.

**The objective entities are flat and name-wired.** Guardians, walkers,
patrons, shrines, trooper spawns and shops are point entities with string
keyvalues, linked to each other by `targetname`, not by element reference.
`citadel_final_objective_proxy` wires the lot with plain strings
(`sub_objective_1 = "125_rebels_titan_yellow"`). `MapEntity`'s existing
string-to-string bag expresses all of it.

## 4. batch13 conventions

Author everything ONCE, for team 2. The twin is generated: same proper
rotation as `mirror.py` about (460.1, 6085.05), `m_` prefix, `teamnumber`
flipped 2/3, `targetname` and `BossName` prefixed. A `check()` fails the run if
anything lacks exactly one twin — authoring the far half by hand is what put
the box plan out of symmetry before.

Lanes take ONE centre route; the three `LaneSlot` files are generated by
offsetting along the segment normal, centred (-96, 0, +96), so slot 1 walks
the line actually drawn and files stay parallel through corners. **That slots
are parallel files is an inference, not read from dl_example.**

Rerunnable: strips everything tagged `_batch13` and rebuilds.

## 6. Open, and the two that can fail silently

- **LANE NUMBERING IS UNKNOWN.** `lanenum` appears NOWHERE in the shipped
  vdata or text; `lane_marker_path`, `lane_number` and `LaneSlot` exist only
  as keyfield names inside `server_strings.txt`, with no value table. The one
  sample is dl_example's 1, 3, 4, 6 — from a FOUR-lane map. The map is three
  lanes. **A wrong lanenum fails silently in game.** Use three of dl_example's
  four rather than inventing 1/2/3, or ask someone who has shipped a 3-lane
  custom map.
- **WALKER CLEARANCE IS UNKNOWN.** `npc_boss_tier2` has `m_navHull = 2`, but
  `nav_hulls.vdata` defines only two hulls and the preset list has two
  entries, so 2 is not an index into it. The physical size is presumably in
  `boss_tier_02_sun_walker.vmdl`, which is compiled and unreadable from CI.
  Nothing in the plan will warn you if a walker does not fit.
- **Every coordinate in batch13 is a PLACEHOLDER**, derived from the two
  spawns so the file runs end to end. The lane goes straight up the middle of
  nowhere. Needs viewer `copy pos` readings.
- Ziplines: the emitter can write them (same `CMapPath` shape, different
  classname) but none are placed.
- `dev_measuregeneric01.vmat` still unconfirmed against the Deadlock tree.
  `dmxconvert` only moves the string, so no run so far could have caught it.

## 7. Things that cost rounds, do not repeat them

- **A survey is only as good as its parser.** The first entity survey used
  `-oe keyvalues2`, which stamps an id on EVERY element, making the "767
  multiply-referenced" figure meaningless; and its line scanner could not tell
  an array scalar from an element type header, because both are one quoted
  token on a line — the difference is only visible on the NEXT line. Both
  reports looked plausible and were wrong. The fix was a one-line lookahead
  and a self-check that asserts a KNOWN value (222 CMapMesh, 767 ids) at the
  end of the run. **Put a known-value assertion in every report.**
- **Prototype the parser on a synthetic sample before shipping it to CI.** Two
  bugs in `lane-probe` (double-escaped newlines, a regex that missed every
  key at the start of a line) were caught this way in seconds.
- I claimed batch13 must run "after mirror, before floormat". The mirror part
  was real; **the floormat part I made up** — floormat and walkcheck read
  boxes and seed on `info_team_spawn`, so batch13 cannot affect them. Check
  before stating an ordering.
- Custom Deadlock maps ship COMPILED (`.vpk` of `.vmap_c`). They cannot be
  read by this toolchain and are not a source of path examples. `dl_example`
  is the only source-format map there is.
