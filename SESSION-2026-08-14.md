# SESSION 2026-08-14 — the maps track, scoped by grilling

Newest session doc wins. Supersedes the maps section of
`SESSION-2026-08-13.md` and `FINDINGS-maps-2026-08-13.md`.

Companion: `FINDINGS-vmap-2026-08-14.md`, which carries the format facts.
This doc carries the decisions.

## 1. What changed

Three corrections, each of which shrank the track:

1. **`.vmap` is DMX binary 9, not KV3.** The vdata layer does not apply.
2. **`dmxconvert.exe` converts KeyValues2 text to binary DMX**, both
   directions, and ships in Source 2 Workshop Tools. **We do not need to write
   binary DMX.** We write text; Valve's tool produces the binary.
3. **The one-box fixture was already in `dl_example.vmap`** — a single quad,
   4 verts / 8 half-edges / 1 face, with every data stream visible.

Net effect: the emitter needs a **binary reader** (for round-trip evidence)
and a **text writer**. The binary writer, which was the scary part, is gone.

## 2. Settled decisions — do not relitigate

| | |
|---|---|
| **"Done" for maps = simple layout maps at a scale portable to Hammer for finishing** | Not compiler acceptance, not in-game load |
| **The GPU limitation was never about rendering** | The phone renders 3D fine. The limitation is that Deadlock is a Windows game. A browser walkthrough is the review loop |
| **Viewer: textured HTML walkthrough, not ASCII** | Orange Source-style dev textures with scale bands, **drawn procedurally in canvas**, never extracted. The ASCII city survives as its own separate project, off the critical path |
| **Source of truth is a JSON box list** | `.vmap` is a build artifact, regenerated. The day Hammer opens it on the Windows machine, Hammer becomes the source and the JSON goes stale by design |
| **Grid guides, it does not constrain** | Origins snap to 64; extents are free. A hard grid would fight verticality, and Deadlock is a verticality game |
| **Read, then round-trip, then emit** | Order is NOT indifferent. Q1 removed the compiler as the definition of done, so the round trip against a fixture we did not author is the only evidence the writer is correct |
| **Binary reader in pure .NET** | Never put a Valve exe on the read path. Text-only would make every read need a Windows runner |
| **Emit KeyValues2 text; `dmxconvert` makes the binary** | Diffable on a phone, and Valve owns the hard half |
| **DMX lives in `Deadlock.Format`** | A new `DmxDocument`, sibling to `Kv3Document`, not inside it. `Kv3Document` remains the ONLY thing touching VRF; `DmxDocument` becomes the only thing touching the DMX reader |
| **`dl_example.vmap` is committed whole** | 15 MB, well under GitHub limits. A fixture CI can use with no fetch step that rots. Provenance recorded in `FIXTURES.md`; no licence was found |
| **Compiler probe is demoted to a warning, not a gate** | It stopped being the definition of done but it is still the only external judge, and it converts a months-long unknown into a same-day signal |
| **Version drift is accepted, not pre-empted** | Fixture is Oct 2024, `editorbuild 10169`. Chasing a newer one is an unbounded search for a problem that may not exist. But on failure, **schema drift is hypothesis #1**, before debugging half-edge code |

## 3. Rejected, with reasons

- **Grid-to-boxes front end built now.** The first geometry target is a sealed
  room with two spawns, which is a dozen lines of hand-written JSON. A grid
  editor is worth building once there is something to feed.
- **`.vmap` as the editing source.** Every wall move would need a working
  read-modify-write through DMX, and the browser viewer would need a DMX parser.
- **Emitting `.obj`/`.fbx` for Hammer import.** Loses editable brushes, which
  is the entire point of "portable to Hammer for finishing".
- **Hard voxel grid.** Ramps, ledges, diagonals.
- **Extracting Valve dev textures for the viewer.** Procedural is 20 lines and
  has no provenance problem.

## 4. THE NEXT THING — in order

1. **`dmxconvert` probe.** Is it in the Reduced CSDK `bin_cs2/win64`, and does
   it round-trip `dl_example.vmap` at `binary 9 / vmap 40`? Two separate
   questions; the second is the one that matters. Every guide found uses it on
   models and particles, **never on maps**. See `probe-dmxconvert.yml`.
2. **Binary DMX reader** in `Deadlock.Format`, plus round-trip against the
   fixture. Floors stated before reading any result: **element count > 7000,
   `CDmePolygonMesh` count = 222.**
3. **VRF map-decompiler survey** (`vmap_c -> vmap`) — only if step 1 failed.
   VRF already ships a `.vmap` writer; if `dmxconvert` works we do not need it.
4. **JSON schema + text writer.** Schema is: unit declaration; boxes
   (`origin` snapped to 64, free `extents`, `material`); entities (`classname`,
   `origin`, `angles`, flat string->string bag). Nothing else.
5. **`resourcecompiler` map probe**, warning-level. Source at
   `content/citadel_addons/<name>/`, NOT `content/citadel/`.
6. **HTML viewer.** Needs no CI and no Windows, so it is the thing to build on
   a phone while a probe is queued. Must not jump the queue.

Plus a CI identity check once 2 and 4 exist: **`.vmap` must round-trip back to
the same box list.** A green export is not a correct export.

## 5. Open, and honestly open

- Does Hammer **read** a text-encoded `.vmap`? Unknown. Worth one Discord
  question; the answer either removes the `dmxconvert` dependency or doesn't.
- The **document floor** — which of `CMapRootElement`, `CMapWorld`,
  `CVisibilityMgr`, `CMapVariableSet`, `CStoredCameras`,
  `CObjectSelectionSetDataElement` are mandatory. The fixture is maximal, so it
  cannot answer this. The round trip will show what the *reader* expects;
  what *Hammer* tolerates stays unknown until hardware exists.
- **Cell size.** Floor reads z=64 in both a mesh origin and a spawn; map spans
  ~31,000 units X by ~8,600 Y. 64 is the working assumption, `[?]` not `[V]`.

## 6. Process note

Two lesson-1 violations were caught *before* building this time, both by
searching: `dmxconvert` already does the binary writing, and VRF already
decompiles `vmap_c -> vmap`. A third was caught by lesson 4: three assumptions
about the DMX wire format died in the first ten minutes of reading real bytes
(KV3, array base 15, uniform string encoding).

The cheapest work this session was the reading. The most expensive thing
avoided was a binary DMX writer nobody needed.
