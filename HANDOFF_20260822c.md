# HANDOFF — lanes, ziplines and the entity survey, session 2026-08-22c

Follows `HANDOFF_20260822b.md`, which covers the emitter, paths and the
CVisibilityMgr finding. This one covers what went INTO the plan: real lane
routes, ziplines, and everything learned about Deadlock's map entities.

---

## 1. What is settled

**All three lanes are real.** Crosshair readings, mid plus both sides. Lane
numbers **1, 3, 6**, chosen from dl_example's 1/3/4/6 because no shipped table
of lane numbering exists anywhere (see §5).

| lane | length | notes |
|---|---|---|
| 1 mid | 22,446 u / 570 m | dogleg east then back west |
| 3 west | 21,554–21,995 u | varies by slot |
| 6 east | 21,857–22,290 u | varies by slot |

Within ~4% across all three.

**Lane paths are SHARED and full length.** dl_example's 16 lane_marker_path
are 4 lanes x 4 slots, each (lanenum, LaneSlot) pair exactly once, and the
class carries NO teamnumber while every team-owned entity does. One path per
lane per slot, both teams walk it in opposite directions. **Do not mirror
lane paths as entities.**

**FOUR slots, not three.** LaneSlot 0–3, and a wave is 4 troopers. They are
parallel files — one route offset sideways, confirmed by the user — not four
independently shaped routes. batch13 offsets at -1.5/-0.5/+0.5/+1.5 x 96 u.

**Side lanes are a MIRROR PAIR.** With 3 lanes and 180 degree symmetry only
mid can map to itself; a route that misses the centre cannot be its own
mirror. So lane 3's far half is lane 6 reversed and mirrored, and vice versa.
Each is authored as its own team-2 stretch and completed from its partner's,
joined at a seam. The measured seam is **306.8 u**, inside the 500 u snap
tolerance, so the partner's duplicate point is dropped and the local reading
wins — one real reading rather than an average.

**ONE zipline per lane, base to base.** Ownership is dynamic in game (a
pushing team can zip most of the map), so the authored teamnumber is a
starting state, not the runtime one. No m_ twin.

## 2. The 8-ziplines-for-4-lanes puzzle, resolved

dl_example has 8 `citadel_zipline_path`. They are NOT two systems:

- **Family A** — 4 x `CMapPath`, 31 child CMapPathNode each, no targetname.
  The live, editable form. Origins are four points 160 u apart on y at
  x -14042, z 896: a Hammer authoring row, not lane geometry.
- **Family B** — 4 x **`CMapEntity`**, no children, the whole route packed
  into a `pathNodes` STRING as rows of 9 floats (pos xyz, in-tangent xyz,
  out-tangent xyz) relative to the entity origin. targetnames `8785_LaneN`,
  and they live inside the 2 CMapGroup. That is what a prefab or instance
  import looks like: 8785 is an id, the group is the paste boundary.

So one cable per lane is correct. This cost several survey rounds; do not
reopen it.

**Tangents are real.** Family B's rows carry non-zero in/out tangents.
batch13 writes ZEROS, which gives straight segments between nodes. Fine for a
blockout; if the cable should sag or curve, that is where.

**Lane colours are not free choices** — the minimap uses them:

| lane | color_tint |
|---|---|
| 1 | 255 106 0 orange |
| 3 | 255 0 0 red |
| 4 | 0 25 255 blue |
| 6 | 139 0 139 purple |

Also `max_simulation_time = 0.2` on every one.

## 3. Zipline node ownership

Nodes carry teamnumber 2, 3 and **4** (38 of 270 at 4). Every teamnumber-4
node is `capturable = 1`; owned nodes split roughly 60/40 not-capturable to
capturable. So **capturable is not ownership** — it marks the stretch that can
change hands as a wave pushes, which is why a winning team ends up zipping
most of the map. Nodes near a base are fixed.

batch13 writes: teamnumber by side with a neutral band of 4 across the middle
(`ZIP_NEUTRAL_HALF_SPAN` 2000 u), capturable within `ZIP_CAPTURABLE_HALF_SPAN`
6000 u. **Both spans are guesses** tuned to land near dl_example's ratios.

`disable_zipping_to = 1` occurs ONLY where `corner_node = 1`: you pass through
a corner, you do not zip to it. batch13 leaves both 0.

## 4. Entity inventory — what is a POINT and what is a VOLUME

Every `trigger_*` and `func_*` holds an inline `CMapMesh` in its children,
the same shape as a shop. batch13 emits these with a `mesh`.

| volume | notes |
|---|---|
| `trigger_item_shop` | teamnumber, AudioOffset |
| `citadel_trigger_idol_return` | urn dropoff AND spawn; the 2 alternate |
| `func_regenerate` | spawn-room regen |
| `trigger_tier3phase2_shield` | patron phase 2 |
| `citadel_zap_trigger` | shot off the zipline. PercentMaxHealthDamage, TimeBetweenShots, ShootAfterEnteringTime, ShootFromEntity. It IS a placed volume, not a global effect |
| `citadel_trigger_speed_boost` | zipline boost, also placed |
| `trigger_midboss_shield` | only 4 keys, no targetname, no teamnumber — presumably found by proximity. Regenerates constantly and is a DPS CHECK, so the volume should be tight enough that a team must commit inside it |
| `citadel_trigger_climb_rope` | climbable rope |
| `trigger_catapult` | jump pad. `target` NAMES the landing entity, `launch_speed` |
| `citadel_trigger_push` | a fan, not a teleporter: `pushdir` + `speed` |
| `trigger_neutral_shield` (7) | objective shields, not yet placed |

| point | notes |
|---|---|
| `citadel_item_powerup_spawner` | bridge buff, rolls one of 4. **ZERO keyvalues.** 2 on the real map |
| `citadel_minimap_boundary` | **ZERO keyvalues.** Without these the minimap has no frame |

Midboss is authored as a CAMP: `info_neutral_trooper_camp` with

**dl_example is a GYM, not a layout.** It shows one of each mechanism
(1 powerup spawner, 1 rope, 1 catapult) where the real map has more. Do not
read its counts as a template — except where they divide evenly by lane,
which the lane paths and ziplines do.

## 5. Open, and the ones that fail silently

- **LANE NUMBERING.** `lanenum` appears NOWHERE in shipped vdata or text;
  `lane_marker_path`, `lane_number` and `LaneSlot` exist only as keyfield
  names inside `server_strings.txt`, with no value table. Using 1/3/6 from
  dl_example's four. **A wrong lanenum fails silently in game.**
- **THE RIFT.** A capture point that spawns troopers, newer than dl_example.
  Not in its 55 classnames — no rift/capture/portal variant. Placeable later
  with no emitter change, but the classname is unknown. Try `npc-probe` with
  needles rift/capture/portal.
- **WALKER CLEARANCE.** `m_navHull = 2`, but `nav_hulls.vdata` defines only
  TWO hulls (`default`, `trooper`, both radius 24 / height 80 / climb 17.5),
  so 2 is not an index into it. Physical size is presumably in
  `boss_tier_02_sun_walker.vmdl`, compiled and unreadable from CI. Use the
  ENGAGEMENT radius for clearance instead: guardian 24 m (945 u), walker
  22 m (866 u), roughly 35 and 32 voxels.
- **Scale confirmed at 39.37 u/m** by two independent sources: the vdata
  gives walker initial sight 866 u and melee attempt 600 u; the wiki gives
  22 m immunity and a 15 m stomp. Four round metres in a row.
- The user measured Sharpshooter's 15 m bonus sitting right at the edge of a
  vulnerability radius, which disagrees with the wiki's 24 m. Possibly
  measured to the hitbox surface rather than the origin. **Their measurement,
  not the wiki, is the one taken in game.**
- Side-lane slots vary in length (lane 3 runs 547–559 m across its four
  files) where mid's are identical. The slot offsets interacting with a route
  that turns. Whether 12 m between outer files matters is a judgement call.
- Trooper move speed unknown, so `TROOPER_SPEED` is 0 and the length report
  prints no times. Probably in npc_units.vdata under the trooper subclass.
- Shop-disables-when-guardian-falls is NOT implemented. That is entity IO —
  `DmeConnectionData`, 89 in dl_example, inline so no ids needed — and the
  emitter does not write it.
- Spawn-room roof removal for the zipline is a GEOMETRY edit, so a batch14,
  not batch13. Needs the roof box names.
- Lane 3's zipline was briefly given its own second-level route (axis_766 /
  _761 / _762 / _790, z 720 down to 280). REVERTED: troopers dropping onto
  the second level can get stuck. Readings kept in the batch13 comment.

## 6. Survey tooling — traps in the dumper

`entity-survey.yml` has cost more rounds than anything else. Three faults,
all fixed, all worth knowing:

1. **Wrong encoding.** The first run used `-oe keyvalues2`, which stamps an
   id on EVERY element, making "767 multiply-referenced" meaningless. Use
   `keyvalues2_noids`.
2. **No lookahead.** An array scalar and an element type header are both one
   quoted token on a line; only the NEXT line tells them apart. Without a
   one-line lookahead the element census is junk.
3. **Containers swallow captures.** The dumper starts a capture at the
   outermost element of a capture type and will not start another while
   inside one. `CMapGroup` was in CAPTURE_TYPES, so a cap of 8 returned only
   4 zipline paths — the other 4 were inside the 2 groups, and the group's
   own excerpt was discarded for having no classname. CAPTURE_TYPES is now
   `CMapEntity,CMapPath,CMapPathNode`. **A container in that list hides
   everything nested in it.**

Also: **TUPLE_SPECS keys on classname**, so two specs for the same class
silently overwrite. Use one wide tuple.

**Every report should assert a KNOWN value.** The survey prints CMapMesh
(want 222) and ids (want 767) at the end of the run. Both were confirmed
against a working parser, and they are what makes a broken parse visible
instead of plausible.
