## 1. The plan is no longer placeholders

Crosshair readings replaced the invented coordinates in batch13. What is real,
what is derived and what is still invented is printed at the end of every
batch13 run, so it never has to be reconstructed from a document:

    READ      lane routes, guardians, walkers, guardian shops, secret shop,
              urn dropoff, base shop, spawn room, team spawn
    DERIVED   trooper spawns, from each lane's first node
    INVENTED  every volume SIZE, all angles, camps, breakables, bridge buffs,
              minimap corners, ziplines, zap and boost volumes, midboss
    ABSENT    shrines, the barrack bosses guarding them, patron

**Volume sizes are all invented.** Positions are real; not one extent was
surveyed. A shop inside a wall is a size fault, not a position fault.

**Angles are invented.** Each objective faces the mirror point, which is the
direction a defender looks down its own lane. Cosmetic if wrong.

**Two legacy team spawns were removed.** The plan carried two unnamed
`info_team_spawn` at placeholder coordinates that were not mirrors of each
other: (25, -530, 435) mirrors to (895.2, 12700.1, 435), while the second sat
at (1494, 4854, 3). batch13 now owns team spawns and strips unnamed ones. That
strip is narrow on purpose — only `info_team_spawn`, only unnamed — and it is
the only place any batch script deletes something it did not create.

## 2. What the objectives actually are

This was wrong for most of the session and is worth stating plainly.

| thing | classname | notes |
|---|---|---|
| lane objective | `npc_boss_tier3` | the one in the middle of a lane. Disables its lane's shop when it dies |
| walker | `npc_boss_tier2` | `_weak` subclass on the SIDE lanes |
| shrine | `destroyable_building` | destructible, curse, releases super troopers |
| shrine guards | `npc_barrack_boss` | guard a shrine, drive NOTHING |
| patron | `npc_boss_tier3` in dl_example | not yet placed |

`npc_barrack_boss` owning no connection in dl_example is not a gap in the
fixture. It drives nothing because it is not supposed to.

**Subclasses are per team.** Team 2 uses the plain name, team 3 the `alt_`
one: `npc_boss_tier2` / `alt_npc_boss_tier2`, and the same for tier3 and
tier1. The vdata shows the pairs differing only in model and scale. `flip_team`
swaps them; before that fix every mirrored objective would have rendered in
the wrong team's colours, and emitted, converted and verified clean.

**Weak walkers on the side lanes.** dl_example does the same on its four-lane
map — `_weak` on lanes 1 and 6, full on 3 and 4, i.e. the OUTER lanes. Here mid
is 1 and the sides are 3 and 6, so the lane numbers differ while the principle
is identical. Do not read the fixture's lane 1 as "mid".

## 3. Naming follows dl_example

Teams are **rebels** (2) and **combine** (3). Lane colours come from the
fixture's own boss names: **yellow 1, orange 3, blue 4, purple 6.**

    rebels_t3_boss_yellow                    combine_t3_boss_yellow
    rebels_t2_boss_orange                    combine_t2_boss_orange
    shop_rebels_t1_purple_shop_item_trigger  shop_combine_t1_purple_...
    base_shop_rebels_item_trigger            base_shop_combine_...

**TWO NAMESPACES, and they must stay separate.** The `m_` prefix is
plan-level bookkeeping — `strip_previous`, `twin_of` and every batch script
key on the entity `name`. dl_example has no `m_` anywhere; it pairs
`rebels_x` with `combine_x`. So the entity name keeps `m_` and the
TARGETNAME swaps the team word instead.

**The team word is NOT a prefix.** dl_example puts it mid-name
(`shop_Sapphire_t1_lanecolor_shop`, `base_shop_teamname`), so the swap is on
the first occurrence ANYWHERE. A prefix-only swap silently fell through to
`m_shop_rebels_...` and would have paired a combine half with a rebels name.
Names with no team word are neutral and keep the `m_` fallback.

One disagreement inside the fixture: lane 3's zipline `color_tint` is red
while its boss name says orange. The BOSS NAMES are followed, because they are
what other entities reference.

## 4. Entity IO — read, built, and gated

`DmeConnectionData`, 89 in dl_example, all ONE shape:

    "outputName"    "string"
    "targetType"    "int"          7 in all 89, six different owner classes
    "targetName"    "string"
    "inputName"     "string"
    "overrideParam" "string"       ABSENT FROM EVERY NOTE IN THIS REPO
    "delay"         "float"
    "timesToFire"   "int"          -1 in all 89

`overrideParam` was in no document here. Writing this element from the old
notes would have produced six attributes where the fixture has seven.

**A SHOP IS NOT WIRED DIRECTLY.** Each owns a relay network:

    <shop>_enable_relay        logic_relay         OnTrigger -> Enable
    <shop>_disable_relay       logic_relay         OnTrigger -> Disable
    <shop>_kill_relay          logic_relay         OnTrigger -> Kill
    <shop>_logic_auto_disable  logic_auto          OnMapSpawn, delay 0
    <shop>_logic_auto_enable   logic_auto_citadel  OnGameInProgress, delay 15

So a shop starts closed, opens 15 s into the game, and anything wanting to
change its state triggers a RELAY. That indirection is why several unrelated
things can drive one shop without knowing about each other. `logic_relay`
carries `StartDisabled 0` and NO spawnflags; both auto classes carry
spawnflags 1.

batch15 generates this for all five shops, mirrored: 50 entities, 56 wires.
Lane objectives fire `OnBossKilled` into their own lane's kill relay — a
design decision, where dl_example routes through `info_super_trooper_spawn`.
Base and secret shops get the network but nothing that kills them.

**THE NO-GUID PROPERTY SURVIVED.** A connection names its target by STRING,
not by element reference, so each `DmeConnectionData` is referenced exactly
once by the entity owning it. path-smoke asserts zero ids on a plan carrying
connections; it is measured, not argued.

**verify compares wires field by field.** The census proves a connection
survived the round trip; it does NOT prove its `targetName` did. Everything is
compared as text except `delay`, the one float, which is compared numerically
because `0` and `0.0` mean the same thing.

## 5. What the vdata gave up

Four probe rounds, three of them wasted on the same mistake: searching for
names somebody GUESSED instead of asking the file what it contains. The round
that worked indexed first.

- **TROOPER SPEED.** The unit is `trooper_normal`, not `npc_trooper`, which is
  why three rounds missed it. `m_flWalkSpeed 248`, `m_flRunSpeed 512`,
  `m_flAcceleration 200`. Lane troopers walk, so 248 is `TROOPER_SPEED`.
  Family: `trooper_base`, `_normal`, `_medic`, `_melee`, `_necro`,
  `trooper_zipline_container`, and neutrals `neutral_trooper_weak/normal/strong`.
- **WALKER CLEARANCE**, and it never needed `nav_hulls.vdata`. The guardian
  block carries `m_flTier1PlayerClipCapsuleRadius 32` and
  `...CapsuleHeight 224` — a real clip volume, not an engagement radius.
  Patron core radius 130, **pit radius 550**.
- **SHRINE = `destroyable_building`**, confirmed outright:
  `models/npc/shrine_amber/shrine_amber.vmdl`, `shrine_sapphire.vmdl`, death
  sounds `Shrine.King.Destroy` / `Shrine.Mother.Destroy`,
  `m_flTrooperJumpRange 700` (the super trooper release), and
  `m_flInvulnRange 450` on a `modifier_citadel_ranged_armor_bonus` with
  `m_bPlayersOnly true` — that is ANTI-CHIP, not clearance. Do not size the
  base room around it.
- **Every trooper carries an eight-way damage table**: `m_VSPlayer`,
  `m_VSTrooper`, `m_VSWatcher`, `m_VSWalker`, `m_VSPatron`,
  `m_VSPatronPhase2`, `m_VSGuardian`, `m_VSShrine`. Guardian and watcher are
  SEPARATE categories.
- **THE RIFT, still open but narrowed.** `citadel_capture_point` and
  `citadel_multi_capture_point` exist in the shipped strings, with RTTI
  `CCitadelTriggerCapturePoint` behind them. The `CCitadelTrigger` prefix
  means it is a VOLUME and needs a mesh. dl_example predates the rift by
  months, so its absence there proves nothing either way. Standing candidate.

## 6. Traps paid for again

- **NO LOOKAHEAD.** A probe indexed ZERO block keys in a file with 379,
  because it required the brace on the same line as the key and vdata puts it
  below. `entity-survey.yml` had already paid for this exact trap. One line of
  lookahead fixed it.
- **A CAPTURE SWALLOWS WHAT IS NESTED IN IT.** `DmeConnectionData` cannot go
  in `CAPTURE_TYPES` — it lives inside a `CMapEntity`, which is one, and a
  capture never starts while one is open. It would report zero connections in
  a fixture with 89. Same shape as the `CMapGroup` fault that hid four
  ziplines.
- **`TUPLE_SPECS` keys on classname**, which comes from `EditGameClassProps`.
  A `DmeConnectionData` has none, so it cannot be tabulated that way at all.
- **ASSERT A KNOWN VALUE.** Every probe now checks that something previously
  read is still visible, so a broken parse is visible instead of plausible.

## 7. The parity check was measuring the wrong thing

An earlier report compared base-to-midpoint TIMES and warned above a 3 s
spread. It reported 7.1 s on lanes whose totals differ by 2%, because the
split is taken at whichever node falls nearest the centre and on the side
lanes that node is 1,800–2,000 u away. It was reporting sampling error.

Replaced with total route length, on the user's call: waves need not meet at
the geometric centre, and on a rotationally symmetric map both halves of a
lane are the same polyline, so they will meet somewhere sensible regardless.
What matters is lane-against-lane length.

    shortest 21553.6 u (547.5 m), longest 22446.5 u (570.1 m)
    spread 893.0 u (4.1%), 3.6 s at 248 u/s — within 5%, comparable

## 9. batch.yml runs a LIST now

`SCRIPTS: batch13.py batch14.py batch15.py`, run left to right, one commit.
It used to run one script named in `SCRIPT`, which meant editing this file
from a phone before every run.

**Order matters and is not alphabetical.** batch13 rebuilds the entity set
from scratch; batch15 reads those entities and attaches wiring. Running 15
first leaves relays pointing at entities about to be deleted and recreated.
batch14 touches only boxes and is independent. It stops at the first failure,
because the plan is edited in place and the commit at the end would otherwise
preserve a half-written file.
