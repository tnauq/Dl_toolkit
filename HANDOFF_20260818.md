# dust2_half handoff — 2026-08-18

State at the end of this session: **1757 boxes**, up from 1058 at the start.

## How this session's work is stored

Everything is in a chain of **27 manual tail scripts**, `apply_batch_20260817.py`
then `b` through `z` then `aa`. They run in that order, each taking the plan
path as its one argument:

```
python3 apply_batch_20260817.py  docs/plans/dust2_half.json
python3 apply_batch_20260817b.py docs/plans/dust2_half.json
...
python3 apply_batch_20260817aa.py docs/plans/dust2_half.json
```

Every script is **name-keyed and idempotent**. Adds skip if the box name is
already present; resizes and trims record the expected pre-edit value and
report `FAIL` rather than corrupting geometry if they find something else.
A full replay from the original 1058-box plan reproduces the shipped JSON
exactly, which is how every delivery this session was built.

`docs/plans/dust2_half.json` in this zip is the result of that full replay.

## Conventions confirmed by measurement, not assumption

- `extents` is **full size**, `origin` is the **centre**.
- Rotation is `Rz(yaw) Ry(pitch) Rx(roll)`. For ramp slabs, **local +x is the
  run** and **positive pitch descends along local +x**. Verified against
  `ramp_29_22_down` and `ramp-slab_53`, both of which land on 213.3.
- Standard door: **253.0 wide by 586.8 tall**. Source assembly is `_d195`,
  which sits in an **x-normal** wall.
- Big arch: **400.1 at the springing, 330.4 clear at the floor**, 586.8 tall,
  springing 485.0 above the sill. Source assembly is `_d468`, which sits in a
  **y-normal** wall.
- **The two arch families have different source wall normals.** Cloning
  `_d468` into a face rotates by `normal - 90`; cloning `_d195` rotates by
  `normal`. Getting this wrong put three arches 90 degrees out in batch v and
  it was not obvious in the numbers, only in the viewer.
- Walls thicker than the 26.7 source get the arch cloned 2 or 3 times across
  the thickness rather than one thin arch floating inside.
- Grid is 26.7. Most real coordinates are multiples of 6.67.

## Three bugs worth not repeating

1. **Mitred bends.** Extending both legs of a bend by the same amount is only
   correct for the *outer* side. On the inner side it runs one wall straight
   through the other and into the bore. Correct approach: for each side,
   intersect the two offset wall lines and end each segment there. The helper
   is `polywalls` in batch v and `mitre_ends` in batch t.
2. **A shell that overshoots its own arch.** When a tunnel meets a wall at a
   skew, the shell has to reach past the wall plane, but if the arch stays
   flush in that wall the shell pokes through it into the room. Either the
   arch is square to the tunnel and the shell ends on it, or the tunnel is
   square to the wall. The final answer here was the second: square stubs.
3. **Mutating shared state in a loop.** `polywalls` originally edited its own
   segment-length list while walking the bends, so the second side computed
   against corrupted values and silently dropped wall segments. Symptom in the
   viewer was "the side paths are not enclosed".

## Viewer

`index.html` was rewritten for performance this session and is **render-side
only** — it never mutates or writes back the plan, so nothing in it can affect
the Hammer conversion.

The bottleneck was **not** box count. Faces were tiled by *world* size capped
at 64x64, so a single ground plate emitted 4096 quads regardless of distance.
Changes: screen-space tiling quantised to powers of two times the cell, a
per-box bounding-sphere frustum cull, a sphere reject in the aim raycast, DPR
capped at 1.5, a `detail` button and a `drawn` readout.

Measured headless over five camera positions on the 1660-box plan:
**64,836 → 10,148 average quads per frame**, geometry time 2370 → 839 ms.

Next lever if it is still slow: `solidAt` and `floorUnder` scan all boxes per
movement substep. A coarse grid bucket would fix it.

## Working style that suited this session

The user works from an iPhone and drives edits by pasting **crosshair
readouts** from the viewer, in the form
`dust2_half @ x y z u (m) on box_name`, usually several at a time with one
instruction per group. Deliver as `dust2.zip` laid out from repo root, always
that filename. Say plainly which files are new and which are replacements, and
say what was *not* verified. When a request is geometrically impossible as
stated, say so and give the numbers rather than silently picking one reading.
